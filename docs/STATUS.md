## Log

### 2026-10-20
- **Test build 0.1.5: edit contact details while merging.** The maintainer asked to fix a phone number or an address during a merge. Each phone number, email, address (Street, City, State or region, Postal code, Country boxes; PO box and extended parts kept), website and chat address is now an editable box next to its keep checkbox, with its type shown (mobile, work, ...); "+ Add a phone number / email address / address / website" adds new ones with a type picker (Mobile, Home, Work, Fax, Other, as Thunderbird's card editor names them). `mergeVCard` takes `edits` (an edited value replaces the line's value and the line keeps its type and other parameters; an emptied value drops the line) and `added` (new lines with their TYPE); `mergeOptions` values carry their type and an address's parts (`adrParts`). 1 new test (72). Driven in headless Edge: an edited number, a new work number and a new address were written as expected and survived a redraw; no page errors.
- **Test build 0.1.4: a sidebar button, and Delete.** The maintainer asked for the add-on's icon in Thunderbird's left sidebar like Daynizer's, and for deleting, not just merging. The background registers a space (`spaces.create`, no permission needed; checked in Thunderbird 158's schema) at every start, since Thunderbird forgets add-on spaces; the toolbar button and Tools menu open the same space (`spaces.open`), so there's one tab, with the old message-the-open-tab path as the fallback. On the duplicates page every card has Delete: it deletes just that card (Undo brings it back) and the page stays on the rest with the checks kept. 5 new tests load the background script with a fake browser API (71). Driven in headless Edge: Delete, then Undo; no page errors.
- **Test build 0.1.3: merging made simple.** The maintainer found 0.1.2's columns and one Apply for several people needlessly complicated and asked for: potential duplicates, check the actual duplicates, pick the card and the info to keep, an option to rename, and a Merge button. Now the list is "Potential duplicates" with Review and Not duplicates per group. Review opens one page: 1. check the cards that are the same person (the ones that look most alike start checked, from `suggestPeople`'s biggest strong-match set; none when nothing matches strongly), 2. keep this card, 3. choose what the merged card has: Name, First name and Last name, organization, job title and nickname as text boxes (prefilled, the other cards' values as suggestions), birthday and anniversary picked, every number, email, chat address, address and website checked, the note. Merge merges only the checked cards; if unchecked cards still look like duplicates, the page stays open on them. `mergeVCard` writes the first and last name into N (keeping its other parts). The person columns, Move to and kept-apart pairs on Apply are gone (`apartPairs`, `personName` removed; undo still clears kept-apart pairs that 0.1.1 and 0.1.2 changes recorded). Driven in headless Edge: an 8-card household merged as 3 cards (renamed Samuel Roe) then 3 more, Not duplicates for the rest, Undo; no page errors.
- **Test build 0.1.2: the sort page made obvious; duplicates within an address book only.** The maintainer had 0.1.1 installed but couldn't see what changed: when the pre-sort put every card in one person, the list and page looked as before, apart from a "Person 1" menu. Now: the group page is titled "Who is who" (or "Merge N cards" for one person), starts with a sentence saying what it found and what to do, shows one column per person named by its fullest name (`personName`), with "Move to..." on each card, then "2. Merge each person" with a tab per person. The list tags every group of 3 or more ("looks like 1 person" or "N people") and offers Sort and merge. The pre-sort (`suggestPeople`) now joins the strongest links first and never joins two sets whose names clash or that hold a "not duplicates" pair, so a card with no name (sharing Sam's email and Pat's cell) joins Sam and doesn't glue Pat to him; a test shows 0.1.1 failed this. Address books: the maintainer pointed out that a person in two address books isn't a duplicate, and other apps agree (Google Contacts won't merge across accounts; Apple Contacts links such cards). `findDuplicates` compares within each address book unless `acrossBooks`; a checkbox on the Duplicates page turns that on (setting `duplicatesAcrossBooks`, off by default). 3 new tests (66). Driven in headless Edge: an 8-card household in one book with a nameless glue card sorted into Sammy Roe (4), Patricia Roe (3) and Alex Roe; Move to, Apply and Undo worked; the cross-book Jane pair showed only with the checkbox; no page errors.
- **Test build 0.1.1: a duplicate group can be several people** (the maintainer: 10 cards that are 2 or 3 real people couldn't be merged as 2 or 3). Matches chain, so a household's shared number and a shared name put several people in one group. Looked first at how others do it: Outlook on the web lists the suggested contacts all checked and you uncheck the ones not to merge; Google Contacts takes suggestions one by one or contacts you pick; Apple Contacts is all or nothing unless you select cards; Salesforce merges up to 3 records chosen from the duplicate set; Duplicate Contacts Manager works in pairs. Built: `groupLinks` (what each pair of cards shares), `namesCompatible` (given names where one starts the other: Sam and Sammy, J and Jane; a shared family name alone doesn't count), `strongLink` and `suggestPeople` (people from strong links only), `apartPairs`. The group page ("Sort and merge") gives each card a person picker (Person 1, 2, ..., New person), pre-sorted, with what each card shares and with whom; each person with two or more cards gets a merge editor tab; a checkbox per card in a merge leaves it out. Apply merges every person and marks the people apart, as one history entry; Undo restores the cards and lets them group again (the kept-apart pairs are stored on the entry). The list says "looks like N people" and offers Sort and merge. 4 new tests (63); driven in headless Edge with a 7-card household (3 people): sorted right, merged, kept apart, undone, no page errors.
- **First build: test build 0.1.0.** Manifest V3 for Thunderbird 128 and later, official APIs only (`addressBooks`, `menus`, `storage`; no Experiment, no host permissions). Opens as a tab from its toolbar button or Tools > Contacts Cleanup (an open tab comes to the front, found by messaging it, so no `tabs` permission). Pages: Duplicates (groups by email, phone in any format, chat address or name; merge page with the card to keep, every value checked, single fields picked, notes added; "Not duplicates" remembered), Phone numbers (international or compact; default country for numbers without a code; the user's own grouping kept outside US and Canada; extensions and unknown numbers listed, left alone), Missing names (from N, organization, nickname or email; editable; one-word email guesses start unchecked), Chat addresses (checkbox per phone contact for its JMP.chat address, mobile number first with a choice, gateway field, Select all phone contacts, Generate JMP.chat address for one person, only its own addresses ever removed; a second tab fixes addresses without `xmpp:` and X-JABBER fields), Chat contacts (asks OMEMO for Thunderbird for each account's names and mode, or explains and links to it), Changes (undo any change; a card changed since asks first) and About. Help text from the plan on the chat pages. Cards are edited line by line, so untouched vCard lines come back byte for byte. Look and theme follow Daynizer: its color tokens, sidebar, toolbar, rows, detail panel and Edit/View/Help menu bar, and View > Theme (Match System, Light Mode, Dark Mode). 59 tests.
- The OMEMO side: OMEMO for Thunderbird's background answers this add-on's id over `runtime.onMessageExternal` (`hello`, `chatNames.preview`, `chatNames.setMode`, `openOptions`); in the public OMEMO repo with 6 tests.
